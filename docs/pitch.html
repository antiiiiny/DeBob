DeBob Repository memory for coding agents

Git remembers what changed. DeBob remembers what the codebase means.

A persistent knowledge graph that lets an AI agent query a repository instead of reading it. The model never receives the implementation — and DeBob measures that rather than claiming it.

The problem

Coding agents are amnesiac

Every session starts from zero. To answer “what does this module do?” or “what breaks if I change this?”, an agent greps, opens files, and re-derives the same structure it derived yesterday — burning tokens each time and producing answers nobody can audit.

The structure of a codebase is stable, knowable, and expensive to rediscover. It should be written down once and queried, not inferred over and over from raw text.

How it works

Deterministic first, model last

Structure is extracted with tree-sitter and Git — no model involved, fully reproducible. Only the final stage sees an LLM, and only ever a targeted slice.

Repository Any Git repo, scanned with ignore rules and a size cap
Static analysis Files, symbols, imports, calls, Git churn
Persistent graph .debob/context.db — SQLite, incremental
Targeted retrieval The slice relevant to one question
LLM reasoning Receives the slice — structure, call graph and the authors' own doc comments. Never the implementation.
Why it holds up

Every fact carries its own provenance

Most “AI understands your codebase” tools blend what was derived with what was guessed into one confident-sounding answer. DeBob refuses to. Each node and edge stores a confidence and a dataSource, and model output is quarantined in its own table, tagged with the provider and model that produced it.

1.0 Imports, exports, declarations Parsed from the AST. Reproducible, no model involved.
1.0 File declares symbol Structural containment — a fact, not an inference.
0.9 Calls, instantiates Name resolution, which isn’t sound under shadowing or overloads. Marked down deliberately.
llm Responsibility, layer Stored separately, never mixed into the structural graph.

And it runs without an API key

The semantic layer normally comes from watsonx. It doesn’t have to: debob enrich hands the graph context to whichever coding agent is already open in the editor, which writes the summaries back. Same table, same downstream behaviour, no credentials — which removes the usual barrier to a tool like this being tried at all.

IBM Bob

Bob built this, and Bob queries it

DeBob was implemented with IBM Bob across its core sub-tasks — the SQLite persistence layer and schema, the repository scanner, the tree-sitter TypeScript and Python analyzers, the Git extractor and graph builder, the engine and CLI, the watsonx.ai adapter, and the review / explain commands.

Bob wrote down what it learned The constraints Bob discovered are committed to the repository rather than left in chat history: that sql.js is in-memory, so the database silently saves nothing unless it is closed; that web-tree-sitter is an exact pin because an ABI mismatch breaks the analyzer at runtime with no error; that the tree-sitter node is import_statement, and the wrong name extracts nothing while raising nothing. That file is itself the thesis — understanding, persisted.
Bob is now a consumer of it DeBob ships two skills built for Bob. debob-query activates on architecture questions — what a file does, what depends on it, which files sit in a layer, which churn most — and answers from the graph without opening a source file. debob-enrich lets Bob write the semantic layer itself, so the AI features work with no watsonx credentials at all. The agent that built the system is now the fastest thing reading it.

Known limits

Where it isn’t there yet

Method calls aren’t resolved A call through a member expression — adapter.close() — needs type information to resolve. Guessing from the property name would invent edges, so DeBob emits none. In object-heavy code, “what calls X?” is genuinely partial.
Language coverage is narrow TypeScript and JavaScript are solid. Python is shallow — imports and definitions only. Nothing else is supported yet.
Validated on two repositories, not many DeBob itself and a 338-file Next.js monorepo. That second repository immediately exposed a real bug — imports of *.api.ts / *.config.ts style filenames were resolving to phantom nodes — which is a fair indication of what a third and fourth repository would still turn up.
The obvious objection

“Context windows are huge now. Why not just let the agent read the files?”

Attention isn’t free, even when context is Accuracy degrades as irrelevant material grows around the relevant part. Precision beats volume, and cost and latency still scale with what you send.
Some questions aren’t retrieval questions at all “Which files are in the data layer?” or “what are the ten highest-churn modules?” can’t be answered by reading files at any context size. They’re queries over a structure, and you need the structure to exist.
The graph persists; a context window doesn’t An agent re-derives structure every session. The graph is written once and read forever — and it carries Git history, which no amount of reading current source recovers.
Try it

The graph ships with the repository

DeBob's own knowledge graph is committed at .debob/context.db, already enriched by watsonx.ai. You can open it without an IBM Cloud account, an API key, or a .env file — the understanding travels with the code, which is the entire point of building it this way. 

$ git clone https://github.com/antiiiiny/DeBob.git
$ cd DeBob && npm install && npm run build
$ node dist/bin/debob.js visualise
  → 299 nodes · 603 edges · 46 watsonx summaries · no credentials

Verified end to end from a clean clone of the public repository. Everything above is the structural graph plus the watsonx enrichment layer; pointing DeBob at a repository of your own is debob init, and adding the semantic layer needs either watsonx credentials or a coding agent already open in the editor.
